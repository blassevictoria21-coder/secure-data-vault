01Introduction & scope

The Secure Data Vault is a web dashboard backed by a relational database that stores highly sensitive records — medical notes and financial files — and is engineered so that the information is protected at rest. If an attacker obtains the database files, a backup, or a SQL dump, they recover neither user passwords nor any record contents.

The project follows the four-step secure engineering pipeline set by the brief:

StepRequirementImplementation
1Database with Users and Records tablesPostgreSQL (Netlify Database); schema in Drizzle ORM, applied by a versioned SQL migration
2SHA-256 + cryptographic salt for new passwords16-byte CSPRNG salt per user; SHA-256(salt ‖ password); constant-time verification
3Symmetric (AES) encryption before writing to diskAES-256-GCM, random 96-bit IV per row, 128-bit tag, owner bound as AAD
4Authorised login → query → decrypt → displaySigned session cookie; owner-scoped query; tag verification; plaintext rendered with textContent
Language choice. The brief lists Python, PHP or Java as examples. The vault is written in TypeScript on Node.js, which calls the same OpenSSL implementations of SHA-256 and AES through the built-in node:crypto module. The algorithms, parameters and storage formats in this manual carry over directly to Python's hashlib/cryptography or Java's MessageDigest/Cipher.

02System architecture

The system has three layers. The browser talks only to the API server over HTTPS. All cryptography runs on the server, and the encryption key never sits in the same store as the data.

HTTPS (TLS) → server memory (plaintext exists only here, briefly) → disk (hashes & ciphertext only). Master key: environment variable or an isolated key store, never the database.

04Step 2 — Password hashing

Registration

  1. The server validates the input: username 3–32 characters from [a-z0-9_.-], password 10–128 characters.
  2. It generates a salt of 16 bytes from the operating system's CSPRNG (crypto.randomBytes).
  3. It normalises the password to Unicode NFKC, so visually identical input always hashes the same way.
  4. It computes hash = SHA-256(salt_bytes ‖ utf8(password)) and hex-encodes it.
  5. It stores password_salt and password_hash. The password itself is discarded.
export function generateSalt(): string {
  return randomBytes(16).toString("hex");            // 128-bit CSPRNG salt
}
export function hashPassword(password: string, saltHex: string): string {
  return createHash("sha256")
    .update(Buffer.from(saltHex, "hex"))               // salt first
    .update(Buffer.from(password.normalize("NFKC"), "utf8"))
    .digest("hex");                                    // 256-bit digest
}

Login verification

  1. The server loads the user's row by username.
  2. It recomputes SHA-256(stored_salt ‖ submitted_password).
  3. It compares the result with the stored hash using crypto.timingSafeEqual, so response time does not reveal how many bytes matched.
  4. For unknown usernames it still hashes against a dummy salt, so attackers cannot find valid usernames by timing.
  5. Every failure returns the same message: "Invalid username or password."
export function verifyPassword(password, saltHex, expectedHashHex) {
  const actual   = Buffer.from(hashPassword(password, saltHex), "hex");
  const expected = Buffer.from(expectedHashHex, "hex");
  return actual.length === expected.length && timingSafeEqual(actual, expected);
}

Why the salt matters

Without a salt, two users with the password Summer2026! would have identical hashes, and an attacker could look the hash up in a precomputed rainbow table. With a unique 128-bit salt per user, identical passwords produce unrelated hashes, and precomputed tables are useless: every guess has to be recomputed separately for every user.

Engineering note. SHA-256 is fast (billions of guesses per second on GPUs). The brief requires salted SHA-256, and that is what is implemented. A production system should add key stretching — PBKDF2-HMAC-SHA-256 with ≥600,000 iterations, scrypt, or Argon2id. The hash_algorithm column exists so stored hashes can be upgraded transparently at the next login (§12).

05Step 3 — Data encryption (AES-256-GCM)

Every sensitive field of a record — title, patient/account holder and body — is serialised into one JSON document and encrypted before the INSERT statement is built. The database never receives plaintext.

ParameterValueReason
CipherAES (Rijndael), 256-bit keyNIST FIPS 197 standard; 2256 key space
ModeGCM (Galois/Counter Mode)Authenticated encryption: confidentiality and integrity in one pass (NIST SP 800-38D)
IV / nonce96 bits, random per writeNever reused under the same key; identical plaintexts give different ciphertexts
Auth tag128 bitsDetects any modification of the ciphertext, IV or AAD
AADsecure-data-vault:record:owner=<id>Cryptographically binds each row to its owner
Encodingbase64 text columnsPortable; easy to inspect in any database viewer
 
export function encryptRecord(plaintext: string, ownerId: number) {
  const iv = randomBytes(12);                                   // fresh 96-bit IV
  const cipher = createCipheriv("aes-256-gcm", keys().aes, iv, { authTagLength: 16 });
  cipher.setAAD(Buffer.from(`secure-data-vault:record:owner=${ownerId}`));
  const ciphertext = Buffer.concat([cipher.update(plaintext, "utf8"), cipher.final()]);
  return {
    ciphertext: ciphertext.toString("base64"),
    iv: iv.toString("base64"),
    authTag: cipher.getAuthTag().toString("base64"),
    keyVersion: 1,
  };
}

// API route — encryption happens BEFORE the INSERT
const sealed = encryptRecord(JSON.stringify({ title, subject, body }), userId);
await db.insert(records).values({ ownerId: userId, category, ...sealed });

Why GCM rather than ECB or CBC

ECB encrypts identical 16-byte blocks to identical ciphertext and leaks patterns. CBC hides patterns but provides no integrity: an attacker with write access can flip bits in a stored row without being detected, and badly implemented padding checks open padding-oracle attacks. GCM is a stream mode with a built-in MAC. Decryption fails unless the ciphertext, IV, tag and AAD are exactly as written, so a tampered or relocated row is refused rather than silently decrypted to garbage.

06Key management

Encryption is only as strong as the secrecy of its key. The vault uses one 256-bit master key and derives a separate sub-key for each purpose with HKDF-SHA-256 (RFC 5869):

master  = VAULT_MASTER_KEY (env var)  ── or ──  CSPRNG key in isolated key store
aesKey  = HKDF-SHA256(master, salt="secure-data-vault/v1", info="records-aes-256-gcm", 32)
hmacKey = HKDF-SHA256(master, salt="secure-data-vault/v1", info="session-hmac-sha256", 32)
  • Separation from data. The key is never written to PostgreSQL. A stolen database dump contains only ciphertext. The preferred source is the VAULT_MASTER_KEY environment variable, stored encrypted by the hosting platform. If it is not set, the server generates a key once and keeps it in a separate Netlify Blobs store; a create-only write guarantees that concurrent cold starts agree on a single key.
  • Key separation. A leak of the session-signing key does not reveal the record-encryption key, and the reverse also holds.
  • Rotation. Every row records key_version. To rotate keys, a new version is introduced, new writes use it, and old rows are re-encrypted in the background, because the version tells the server which key to use for decryption.

07Step 4 — Secure retrieval

  1. The user signs in. The password is verified as described in §4.
  2. The server issues a session token base64url({uid, exp}).HMAC-SHA-256(hmacKey, body) in a cookie marked HttpOnly; Secure; SameSite=Strict, valid for 30 minutes.
  3. The dashboard calls GET /api/records. The server checks the HMAC and expiry, which gives it the user id.
  4. It runs a parameterised, owner-scoped query: SELECT * FROM records WHERE owner_id = $1 ORDER BY created_at DESC.
  5. For each row it calls decryptRecord(row, userId). GCM verifies the tag, including the owner AAD, before releasing any plaintext.
  6. Verified rows are returned as JSON over HTTPS with Cache-Control: no-store. Rows that fail verification are flagged and never displayed.
  7. The browser renders every value with textContent, never innerHTML, so stored content cannot run as script (XSS).
const rows = await db.select().from(records)
  .where(eq(records.ownerId, userId)).orderBy(desc(records.createdAt));

const decrypted = rows.map((row) => {
  try {
    const data = JSON.parse(decryptRecord(row, userId));   // throws on bad tag
    return { ...meta, integrity: "verified", ...data };
  } catch {
    return { ...meta, integrity: "failed" };              // tampered → refused
  }
});

The dashboard also has a Show stored ciphertext toggle on every record, which puts the plaintext and the bytes on disk side by side, and a Tamper test that flips one bit and re-assigns the owner in memory to show GCM rejecting both.

12Limitations & future work

  • Key stretching. Move from single-pass salted SHA-256 to Argon2id or PBKDF2-HMAC-SHA-256 (≥600k iterations), upgrading each stored hash when the user next logs in, tracked by hash_algorithm.
  • Envelope encryption. Give every record its own data key, wrapped by a master key held in a hardware-backed KMS/HSM, so keys can be rotated without re-encrypting every row.
  • Brute-force protection. Add per-account and per-IP login throttling and optional TOTP second factor.
  • Audit trail. An append-only access log recording who decrypted which record, and when.
  • Searchable encryption. Blind indexes (HMAC of normalised terms) to search encrypted fields without decrypting them.

Within the scope of the brief, the vault meets every requirement. Passwords are protected by a unique cryptographic salt and SHA-256. Every sensitive field is encrypted with authenticated AES-256 before it reaches the disk. Only an authenticated owner can turn their own ciphertext back into readable records.
